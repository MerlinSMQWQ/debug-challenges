## 1 赛前文档：理解这个系统所需的知识

### 1.1 进程为什么需要边界

操作系统让每个进程拥有自己的执行位置、内存和一组打开的资源。启动另一个程序后，两个进程可以各自运行；父进程调用了启动函数，不意味着子进程已经完成任务。进程编号 PID 用于辨认现场中的具体进程。

在这个小系统中，调度程序负责启动工作程序、归档诊断记录、保存最后的结果；工作程序负责读取输入并进行业务转换。两者通过输入文件、输出文件和标准流传递信息。文件已出现、某条日志已打印、程序已退出，是三种不同的状态。

`Popen(...)` 创建子进程并返回对象；`poll()` 在进程仍运行时返回 `None`，退出后返回退出码；`wait()` 等待退出并返回退出码。退出码为 0 在本题表示程序完成；它不能替代对业务结果的检查。[Python 3.9 subprocess 官方文档](https://docs.python.org/3.9/library/subprocess.html#subprocess.Popen)

### 1.2 标准流与文件描述符

标准输入、标准输出、标准错误分别通常对应文件描述符 0、1、2。文件描述符是进程用来访问打开资源的编号，不是内容本身。输出可以连接终端、文件，也可以连接管道。

stdout 与 stderr 是两个独立通道；stderr 上的信息不必是致命错误，也可以是诊断或审计记录。下例只是说明两个通道的分工：

```python
import sys
print("42")                         # stdout：供调用方使用的结果
print("processed one item", file=sys.stderr)  # stderr：诊断信息
```

Python 中 `stdout=PIPE`、`stderr=PIPE` 会分别建立管道，把子进程的对应输出接到父进程可读取的流上；父进程持有的是读端。[Python 标准流](https://docs.python.org/3.9/library/sys.html#sys.stdout)、[PIPE 的定义](https://docs.python.org/3.9/library/subprocess.html#subprocess.PIPE)

### 1.3 数据怎样经过 I/O 边界

可以把一次输出理解成：程序生成数据 → 语言运行时的缓冲 → 操作系统中的目标资源 → 接收方读取。

缓冲使很多小操作可以合并，但数据进入某层缓冲不等于另一端已经收到。Python 的 `flush=True` 请求刷新语言层缓冲，`python3 -u` 让标准输出和标准错误使用无缓冲模式；这些操作不改变操作系统资源的容量和读取规则。非交互 stdout 通常采用块缓冲，交互 stdout 通常采用行缓冲。[Python 3.9 sys 文档](https://docs.python.org/3.9/library/sys.html#sys.stdout)

管道是操作系统维护的有限字节队列，没有消息边界。一次写入可以被多次读取，多次写入也可能被一次读取取走。默认阻塞模式下：

- 有数据时，读取可以取走数据；暂时没有数据且仍有写端时，读取可以等待。
- 写入需要队列空间；空间不足时，写入可以等待接收方取走数据。
- 所有写端都关闭，且已有数据已读完时，读取才得到流结束 EOF。EOF 与“现在没有新数据”不同。

这些是通道的一般规则，不代表正在运行的程序一定处于哪一种状态。操作系统、缓冲容量和输出量共同影响实际表现，本题不需要背诵某个固定容量。[POSIX read](https://pubs.opengroup.org/onlinepubs/9799919799/functions/read.html)、[POSIX write](https://pubs.opengroup.org/onlinepubs/9799919799/functions/write.html)

Python 流的 `read(n)` 请求至多 n 个字符或字节；没有长度参数的 `read()` 会读取到 EOF。文件通常有确定的末尾；来自另一个进程的流，其末尾还取决于写端生命周期。[Python I/O 文档](https://docs.python.org/3.9/library/io.html#io.BufferedIOBase.read)

### 1.4 状态由谁持有，什么时候变化

| 状态 | 持有者 | 发生变化的操作 |
| --- | --- | --- |
| 当前输入行、累计业务结果 | 工作进程 | 读取、转换与计数 |
| 子进程 PID、退出状态、已取得的输出 | 调度进程 / subprocess 对象 | 启动、读取、等待 |
| 流中的在途字节、端点是否开放 | 操作系统 | 写入、读取、关闭端点 |
| 语言层尚未送出的数据 | 对应进程的 Python 运行时 | 写入、刷新、关闭 |
| CSV、日志、结果文件 | 本地文件系统 | 打开、写入、刷新、关闭 |

没有必要在调查开始前掌握整个操作系统。需要能说明一个操作正在等待什么，以及使它继续的条件由谁改变。进程仍存在不等于正在做计算；低 CPU 也不等于程序已经完成。

### 1.5 允许工具的最小用法

下列 `PID` 是你从实际启动输出或进程列表获取的编号，不是固定值。

```sh
python3 --version
python3 lab.py --help
python3 lab.py run --help
ps -p PID -o pid,ppid,state,%cpu,rss,command
lsof -p PID
kill -USR1 PID
```

本题的两个业务程序都已注册 `SIGUSR1`：它会把当前 Python 调用栈写入本次运行目录内相应的 `.stack` 文件，并继续运行。`.stack` 在未请求快照时可以是空文件。信号只发给本题的实际 PID；`Ctrl-C` 用于结束当前运行。注册语义见 [faulthandler 官方文档](https://docs.python.org/3.9/library/faulthandler.html#faulthandler.register)。

可以用 `cat`、`tail`、`rg`/`grep`、`diff` 查看材料，用文本编辑器阅读或修改源码，用 `python3 -m pdb job.py ...` 单步调试。调试器、额外日志和修改都会改变现场，应保留改动和实验目的。这些工具提供事实，解释仍需要你的系统模型。

## 2 事故说明

某团队用本地批处理把门店发票转换为结算文件。小批次试跑成功，但当天的完整批次一直停在“进行中”。调度日志记录了任务启动，之后没有完成记录，也没有明确的失败记录。现场运行尚未结束时，两个业务进程仍然存在，CPU 占用很低。

准备阶段在本机实际观察到：`small` 成功完成；`daily` 在 8 秒观察窗口内没有完成，被测试保护停止。这里的 8 秒是复现程序的保护时限，不是声称任务会在第 8 秒自行失败。

你需要解释异常如何产生，给出可核对的证据和修复。不能只把任务重启、超时或某条可疑代码当作根因结论。

### 2.1 正常行为与业务契约

一次任务读取指定 CSV 和配置，完成后退出码为 0，产生以下文件：

| 输出 | 正常行为 |
| --- | --- |
| `exported.csv` | 按原顺序保留支持币种的完整输入行，不重复、不遗漏 |
| `summary.json` | 包含输入数、导出数、拒绝数和各支持币种的整数分金额合计 |
| `worker.log` | 每个拒绝行都有一条 JSON 审计记录：`event=rejected`、`reason=unsupported_currency`、`row` 为完整原行 |
| `job.log` | 记录启动、工作进程编号；成功时包含 `job_completed` 事件 |

配置支持 CNY、USD、EUR。其他币种按正常业务规则拒绝，不属于运行失败。输入字段为 `invoice_id/account/currency/cents/note`，`cents` 是整数分，避免浮点货币误差；不需要财务知识。

正常程序应能在本机 8 秒内完成两组参考输入。这个小系统不访问网络、不调用外部服务，也不需要数据库。修复必须保持输出契约及审计完整性。

### 2.2 可调查的现场

- `job.py`、`exporter.py`：业务源码，共约 100 行；没有省略关键路径。
- `config.json`、`data/small.csv`、`data/daily.csv`：完整配置与输入。
- `lab.py`：运行、超时保护及重置；`verify.py`：按外部输出验收。
- `evidence/initial/`：出题准备阶段一次真实事故运行的启动日志和观察记录，未加入诊断结论。
- `runtime/`：你新运行产生的文件、日志、进程状态和按需获取的栈。
- `ENVIRONMENT.md`：实测版本、依赖及验证范围。

这里开放的源码与现场没有隐藏组件。允许工具能获取的证据均可获取；无需向出题者申请解锁。`organizer/` 是分离的赛后材料，赛前不阅读或搜索该目录。

### 3.2 启动与稳定复现

```sh
python3 lab.py run small --timeout 8
python3 lab.py run daily --timeout 8
```

命令在前台运行，并打印本次任务 PID。每组的输出保存在 `runtime/small/` 或 `runtime/daily/`。两组可以先后运行；同一组再次运行之前需要重置。超时退出码为 124，只表示运行保护停止了仍未完成的任务。

需要保留正在运行的现场时，在一个终端执行：

```sh
python3 lab.py reset
python3 lab.py run daily --timeout 0
```

`--timeout 0` 不设置运行保护。可在另一个终端使用允许工具观察；结束时回到运行终端按 `Ctrl-C`，运行器会终止它创建的本题进程组。它不使用名称匹配去终止其他项目的程序。

### 3.3 重置

```sh
python3 lab.py reset
```

重置只清除本题 `runtime/`，保留源码修改、配置、输入和初始证据。先复制需要保留的实验输出到自己的调查记录目录。运行器发现仍有活动任务时会拒绝重置，应先在原终端结束该运行。

重置不是恢复原始源码。首次修改前，可以在本题目录内保存一份自己的源码备份。原始事故文件哈希见 `ENVIRONMENT.md`；不得通过赛后材料恢复或比对答案。

### 3.4 按外部行为验收

```sh
python3 lab.py reset
python3 verify.py
```

验收独立读取输入计算期望结果，不依赖业务程序内部函数，不要求采用特定修复。两组均应完成，导出行、计数、金额及完整拒绝审计应一致。全部通过退出码为 0；失败退出码为 1，并提示查看对应运行目录。

验收使用固定配置与输入校验值。为了实验可以使用自己的副本，但最终验收不能靠修改参考输入、支持币种、验收脚本或保护时限过关。延长超时、遗漏业务记录或丢弃审计记录不满足正常行为契约。验收通过是提交的证据之一，不能替代根因解释。
