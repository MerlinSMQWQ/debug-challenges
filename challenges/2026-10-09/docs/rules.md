# 比赛规则与提交

本题遵循[Debug 挑战赛手册](../../../Debug%20挑战赛手册.md)。下面列出本题的具体条件。

## 时间和难度

综合难度 **Medium**；知识难度 ★★☆☆☆，推理难度 ★★★☆☆。赛前材料补齐必要系统知识，调查需要把代码与现场观察连成因果链。

时限采用标准档 **45 分钟**。参赛者明确开始时记录开始时间，学习和环境准备不计时。运行脚本的 8 秒保护与比赛计时分别记录。

时限内完成记“限时完成”，超时后仍可继续，记“超时完成”。时间不直接换算为能力分。本次交付仅完成赛前准备，不包含参赛者开始时间、提交或成绩。

## 工具和调查范围

采用手册 **C 档：系统调试**，本题开放的具体工具如下：

- Docker Desktop 或 Docker Engine、宿主机文本编辑器；阅读或修改题目源码，运行程序，自写最小实验。
- 题目容器内的 shell、Python 标准库、`cat`、`tail`、`rg`、`grep`、`diff`、`ls`、`find`、`wc`、`ps`、`top` 和 `lsof`。
- 使用 `docker compose run --rm challenge stack ...` 获取业务进程的 Python 栈；可以在容器内使用 Python 自带调试器 `pdb`。

业务源码、配置、输入、Docker 配置、运行脚本、验收标准和真实运行产物全部开放，不需要申请解锁证据。实验限于本项目及题目容器；不得操作其他项目、容器或用户进程。本题不开放 `lldb`、`gdb`、`strace`、`dtrace`、`perf`、`tcpdump`，不需要云服务器、容器内 root 或宿主机管理员权限。

允许查阅 `man`、`--help`、Python 官方文档和 POSIX 的一般规则与接口语义。普通挑战中，禁止搜索当前故障的现成答案，或让另一个 AI 分析本题源码、解释异常、猜根因、推荐调查路径。赛前学习可以用 AI 理解一般知识；AI 辅助挑战须另行明确标记、独立记录成绩。

赛前禁止阅读或搜索 `organizer/`。最终验收不得改变参考输入、币种配置、验收标准或保护时限来宣称修复；修复需要保留完整业务结果和审计。

## 提示

卡住时可以申请第 1、2、3 级提示，依次提供方向、建议获取的证据、需要检查的机制。提示逐级按请求给出，不直接公布根因。

申请次数和级别单独记录，不自动扣分。参赛者能够通过允许工具获取的真实证据，应当正常开放，不因提示级别而扣留。

## 调查记录与提交

在 `notes/` 简要记录观察、假设、预测、实验、结果和判断更新。区分实际取得的事实与当前解释；证据不足时可以说明暂时不知道。

正式提交包含以下五项，并附必要日志、实验输出和补丁：

```text
ROOT CAUSE 根因
具体缺陷或错误条件是什么？

MECHANISM 因果机制
它改变了哪些状态，怎样导致当前症状？

EVIDENCE 证据
哪些观察支持结论，怎样区分其他合理假设？

TRIGGER 触发条件
什么输入、时序、配置或运行状态会触发？

FIX 修复
修复为何有效？外部验收结果如何？实际工程中有什么取舍？

附加记录
用时 / 45 分钟；完成状态；提示次数与级别；AI 使用模式。
```

## 评分与复盘

沿用手册的 100 分标准：根因 30、因果机制 20、证据链 15、假设质量 10、实验设计 10、系统模型 10、修复 5。用时和提示另行记录。

评价重点是有证据的判断、有效实验、寻找反证和修正理解。只指出某行代码或让症状消失，还不足以解释故障。

提交并结束挑战后，公开预先固定的故障真相，说明正常系统、故障注入、触发条件、完整因果链和证据，再对照实际调查过程讨论修复与可迁移的方法。
