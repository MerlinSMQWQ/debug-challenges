# 环境与验证记录

2026-10-10 将赛题环境统一为 Docker 中的 Linux。以下是出题准备结果，比赛尚未开始，没有参赛者提交或成绩。

## 固定环境

| 项目 | 当前约束 |
| --- | --- |
| 比赛操作系统 | Docker 镜像内的 Debian Linux（Bookworm） |
| Python | 镜像内 Python 3.13 |
| 宿主机 | Windows、macOS 或 Linux，只负责运行 Docker 与编辑文件 |
| 外部服务 | 无；不需要云服务器、数据库或网络 API |
| Python 依赖 | 仅标准库 |
| 调查工具 | 镜像内置 `ps`、`top`、`lsof`、`rg` 等 |

Windows 参赛者使用 Docker Desktop 的 Linux containers。所有宿主机使用同一个 `Dockerfile` 和 `compose.yaml`，因此题目不再依赖宿主机的进程信号、Python 版本或命令行工具差异。

## 环境修复了什么

旧版本把 macOS 本机当成最低条件，并要求参赛者向 PID 发送 `SIGUSR1`。当前版本把 Linux 容器固定为比赛边界；栈快照改成共享目录中的请求文件和标准库诊断线程，两个 Compose 容器可以协作取得真实调用栈。

Compose 挂载源码目录，参赛者可以正常编辑和验证修复。活动任务标记会阻止另一个容器清理现场；异常退出后必须显式使用 `reset --force`。仓库还固定了文本文件的 LF 换行，避免 Windows Git 配置改变参考输入字节。

## 验证范围

- Docker 镜像能够从仓库配置构建，不需要题外服务。
- 事故版本的样例批次完成，日结批次在保护时限内未完成。
- 第二个临时容器可以分别请求调度程序和转换程序的真实 Python 栈。
- 到达运行保护时限后，活动标记被清除，任务容器可以安全移除。
- 标准验收能区分事故版本和正常基线，并检查记录、汇总、金额和完整审计。
- 参考输入或配置被改动时，验收明确拒绝继续。

当前验证在本机 Docker Desktop 的 Linux 容器完成；仓库的 [GitHub Actions](../../../.github/workflows/challenge-001-container.yml) 还会从零构建同一镜像并运行环境测试。推送后的工作流结果将作为当前提交的独立验证。

业务配置和两组参考输入保持原样。当前交付是含故障的事故版本，运行产物已清理；初始事故记录来自该 Linux 容器。答案、正常版本和含诊断的原始验证记录保存在分离的出题者目录。
